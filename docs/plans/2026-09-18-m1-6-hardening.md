# M1.6 — Hardening: Plano de Implementação

> Para o agente executor: implementar um incremento por vez. Ao final de cada incremento, apresentar relatório com arquivos, testes, resultados e pendências; aguardar aprovação antes do próximo.

**Goal:** Validar e endurecer o Marco 1 contra regressões de segurança, vazamento entre clínicas, exposição de segredos, falhas operacionais e ausência de observabilidade.

**Base:** árvore pós-merge equivalente a `origin/main` em `2392ac6`; inclui os commits extras de PWA/polimento da `feat/m1-5-frontend-operacional`.

**Spec:** `plan.md` §§3–5 · `docs/security.md` · ADRs 0002–0008 · M1.5 frontend operacional.

**Tech stack:** Node.js 24.19.0 · pnpm 11.10.0 · Playwright · Next.js 15.5.25 · Python 3.12.14 · FastAPI · PostgreSQL 17 · Docker Compose · uv.

## Decisões travadas

- Playwright rodará contra o Compose completo, com fixtures híbridas e determinísticas.
- Uma conta terá memberships em duas clínicas para validar o seletor.
- Contas restritas a uma clínica tentarão acessar a outra por URL e API.
- Logs serão JSONL com allowlist de campos, usando bibliotecas padrão.
- CSP será bloqueante, com nonce e sem `unsafe-inline` para scripts.
- Restauração usará `pg_dump -Fc` e `pg_restore` em PostgreSQL descartável.
- Auditorias atuais serão mantidas e complementadas por scanner reprodutível de secrets.
- Workers Playwright serão serializados para evitar estado compartilhado imprevisível.

## Global constraints

- O navegador continuará acessando a API somente por same-origin `/api/v1`.
- Nenhum token, senha, cookie, header `Authorization`, corpo de requisição, e-mail ou IP bruto poderá aparecer em logs.
- HSTS será emitido somente em produção.
- A role runtime continuará sem DDL, sem `BYPASSRLS` e sem privilégios de migration.
- Dados E2E serão sintéticos, namespaced e removidos ao final da execução.
- O M1.6 não aprova produção: storage, SMTP, retenção de backups, criptografia e gestão externa de secrets continuarão documentados como pré-requisitos operacionais.
- Cada incremento termina com o gate global aplicável e relatório de aprovação.

- Modificar: `package.json`
- Modificar: `pnpm-lock.yaml`
- Modificar: `.github/workflows/ci.yml`

**Interfaces:**

- `pnpm e2e` executa a suíte contra `E2E_BASE_URL`, padrão `http://127.0.0.1:3000`.
- O serviço Compose `e2e-seed` usa exclusivamente a conexão de migration.
- O seed retorna um manifesto temporário com e-mails, IDs e senhas sintéticas; o manifesto não é versionado.
- O helper Mailpit busca mensagens por destinatário e timestamp, extrai o token do fragmento e nunca imprime o corpo do e-mail.
- Playwright usará `workers: 1`, trace e screenshot em falha.

**Fixtures:**

- Clínica A com identificador e texto sentinela exclusivos.
- Clínica B com identificador e texto sentinela diferentes.
- Usuário multi-clínica com membership ativa nas duas clínicas.
- Usuário exclusivo da Clínica A.
- Usuário exclusivo da Clínica B.
- Usuário não verificado para o fluxo de confirmação.
- Usuário com senha para recuperação.
- Estado inicial criado pelo seed e limpo pelo teardown.

**Cenários obrigatórios:**

- Login válido, login inválido e redirecionamento para área autenticada.
- Recuperação: solicitar reset, localizar e-mail no Mailpit, abrir fragmento, redefinir senha e autenticar novamente.
- Verificação: solicitar/reprocessar link, consumir token e confirmar estado verificado.
- Convite: convidar pela tela de equipe, abrir e-mail, aceitar convite e verificar membership.
- Seletor: usuário multi-clínica visualiza exatamente as duas clínicas e alterna entre suas rotas.
- Settings: leitura, atualização autorizada e confirmação visual do novo valor.
- Equipe: listagem, convite, alteração de papel, remoção e mensagens de erro.
- Sessões: listar dispositivos, revogar sessão remota, revogar sessão atual e executar logout global.
- Tokens de convite/reset/verificação nunca permanecem na URL após processamento.
- Cookie de sessão não aparece em `document.cookie`.
- Usuário de uma única clínica recebe 404 ao acessar a outra clínica por rota/API.
- A resposta e o DOM do usuário restrito não contêm os sentinelas da clínica protegida.

**Gate:** Compose saudável, migrations aplicadas, `./scripts/verify-compose-health.sh` verde e `pnpm e2e` verde.

**Commit sugerido:** `test(web): add Compose Playwright security flows`

## Incremento M1.6.3 — Headers de segurança API e web

**Arquivos:**

- Criar: `apps/api/app/platform/security_headers.py`
- Criar: `apps/api/tests/test_security_headers.py`
- Criar: `apps/web/src/middleware.ts`

- Criar: `apps/web/src/lib/security-headers.test.ts`
- Modificar: `apps/api/app/application.py`
- Modificar: `apps/api/app/platform/middleware.py`
- Modificar: `apps/web/next.config.ts`
- Modificar: `docs/security.md`

**Contrato API:**

Toda resposta HTTP da API, incluindo erros, emitirá:

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`
- `Cross-Origin-Opener-Policy: same-origin`
- `Cross-Origin-Resource-Policy: same-origin`
- `Content-Security-Policy: default-src 'none'; base-uri 'none'; frame-ancestors 'none'`

Em produção também emitirá:

- `Strict-Transport-Security: max-age=31536000; includeSubDomains`

**Contrato web:**

- Gerar nonce por resposta.
- Propagar nonce para scripts e estilos gerados pelo Next.
- Usar CSP bloqueante sem `unsafe-inline` para scripts.
- Permitir somente recursos same-origin, imagens `data:` quando necessárias pelos ícones e conexões same-origin.
- Bloquear `object-src`, `frame-ancestors`, formulários externos e origens externas.
- Excluir rewrites `/api/v1` do middleware de CSP do Next para preservar os headers da API.
- Manter HSTS condicionado a produção.

**Testes:**

- Respostas 200, 401, 404, 422 e 429 da API contêm os headers.
- Health check, páginas públicas e páginas autenticadas da web contêm os headers.
- CSP contém nonce válido, não contém `unsafe-inline` em scripts e não permite origem externa.
- Desenvolvimento não emite HSTS.
- Configuração de produção emite HSTS.
- Nenhum fluxo Playwright apresenta violação CSP.

**Commit sugerido:** `feat(security): enforce API and web security headers`

**Contrato JSONL:**

Cada evento terá, quando aplicável:

```json
{
  "timestamp": "2026-09-18T12:00:00.000Z",
  "service": "api",
  "level": "INFO",
  "event": "http.request",
  "request_id": "uuid",
  "method": "GET",
  "route": "/api/v1/clinics/{clinic_id}",
  "status_code": 200,
  "duration_ms": 12
}
```

Campos permitidos:

- serviço, ambiente, timestamp, nível, evento;
- request ID;
- método, rota sem query string, status e duração;
- tipo de erro e código HTTP;
- UUIDs de usuário/clínica somente quando necessários para diagnóstico.

Campos proibidos:

- corpo de requisição/resposta;
- cookies e `Set-Cookie`;
- tokens, senhas e headers de autorização;
- e-mails e IPs brutos;
- query strings;
- mensagens de exceção contendo dados de entrada.

**Tarefas:**

- Implementar formatter JSON com `logging` padrão do Python.
- Consolidar request ID e access log em middleware próprio.
- Desativar access log textual duplicado do Uvicorn.
- Sanitizar metadata da auditoria por allowlist de evento.
- Ignorar campos desconhecidos em metadata, em vez de serializá-los cegamente.
- Emitir logs de servidor Next em JSON, sem logs de browser.
- Garantir que erros de rede e exceções não serializem objetos de request inteiros.

**Testes:**

- Cada linha capturada é JSON válido.
- Eventos possuem os campos obrigatórios.
- URLs com query sensível não aparecem.
- Senhas, tokens, cookies, IPs e e-mails sintéticos usados nos testes não aparecem em logs nem auditoria.
- Eventos existentes (`login_succeeded`, `password_reset_completed`, `invitation_accepted`, `session_revoked`) continuam registrados.
- Logs de API e web podem ser correlacionados pelo request ID quando houver encaminhamento.

**Commit sugerido:** `feat(observability): add structured redacted logging`

## Critérios de conclusão do M1.6

O marco somente será concluído quando:

- todos os fluxos web definidos passarem no Playwright contra o Compose;
- headers API/web estiverem presentes e CSP não gerar violações;
- logs forem JSON válido e não contiverem dados sensíveis;
- backup customizado restaurar em banco limpo;
- migrations, grants e RLS sobreviverem à restauração;
- revisão de dependências, licenses e secrets estiver verde;
- threat model e runbook estiverem atualizados;
- uma conta restrita à Clínica B não conseguir acessar dados da Clínica A por API, SSR, rota web ou consulta sob a role runtime;
- os testes confirmarem que IDs conhecidos, URLs adulteradas e requests diretos não revelam existência ou conteúdo da outra clínica.
